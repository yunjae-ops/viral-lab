# DECISIONS.md — 설계 결정 기록 (ADR)

각 결정은 다음 형식.

- **상태:** proposed / accepted / superseded
- **날짜:** YYYY-MM-DD
- **맥락:** 왜 이 결정이 필요한가
- **결정:** 무엇을 하기로 했는가
- **대안:** 고려했지만 안 쓴 것들
- **비고:** 초보자 관점 부연

> 용어: ADR = Architecture Decision Record. "이 결정을 왜 했는지"를 나중에도 알 수 있게 남겨두는 짧은 노트.

---

## D-001 · 개발 순서는 Review → Scout 고정

- **상태:** accepted
- **날짜:** 2026-08-21
- **맥락:** 두 기능을 병행하면 초보자 입장에서 코드베이스가 급격히 복잡해지고, 잘못된 구조가 조기에 굳는다.
- **결정:** Review가 실사용 검증(Phase 7)까지 끝난 뒤에만 Scout 관련 폴더·의존성(Supabase 포함)을 추가한다.
- **대안:**
  - 병행 개발 → 탈락. 인지 부하·의존성 뒤엉킴 위험.
  - Scout 먼저 → 탈락. 실제로 매일 쓰는 건 Review.
- **비고:** Review가 안정될 때까지 `app/scout`, `lib/scout`, `@supabase/*` 패키지 모두 저장소에 없어야 한다.

## D-002 · Portfolio 집계는 코드가 계산, AI는 자유서술만

- **상태:** accepted
- **날짜:** 2026-08-21
- **맥락:** SPEC 초안에서는 Portfolio 전체를 AI에게 맡길 수도 있었다. 그러나 개수·비율·경고 판정은 결정적이며, AI가 계산하면 오차·재현성 문제·비용이 커진다.
- **결정:**
  - 카테고리별 개수·비율·과사용 경고 → 서버 코드에서 계산.
  - "다음 소재에서 비어 있는 방향 추천" 자유서술 문단만 Claude 호출 1회로 생성.
- **대안:**
  - 전부 AI에게 위임 → 탈락. 숫자가 종종 틀린다. 사용자가 신뢰 못 함.
  - 전부 코드로 계산 → 탈락. "다음 방향 추천"은 규칙으로 만들기 어렵다.
- **비고:** 이렇게 하면 Portfolio는 항상 결정적으로 검증 가능하고, Claude 호출은 딱 1회로 비용이 안정된다.

## D-003 · 초기 차트는 Chart 라이브러리 없이 CSS 막대로 그린다

- **상태:** accepted
- **날짜:** 2026-08-21
- **맥락:** Recharts/Chart.js 등을 초기부터 도입하면 번들이 커지고, 초보자가 알아야 할 개념이 늘어난다.
- **결정:** Phase 5의 막대차트는 Tailwind의 `w-[35%]` 같은 단순한 div bar로 그린다. 필요가 명확해질 때만 라이브러리 도입 검토.
- **대안:**
  - Recharts 초기 도입 → 탈락. 지금 필요한 만큼보다 훨씬 무겁다.
- **비고:** 사용자에게 "예쁜 차트가 꼭 필요하면 나중에 언제든 붙일 수 있다"고 설명.

## D-004 · Diagnostic 카테고리는 초기 자유서술, 나중에 enum으로 승격

- **상태:** proposed *(사용자 확정 필요)*
- **날짜:** 2026-08-21
- **맥락:** Hook Code A–M, 감정 태도, 화자 인칭, 정보 공개 방식의 최종 목록이 아직 확정 안 됐다. 지금 enum으로 굳히면 나중에 바꿀 때 스키마 마이그레이션 부담.
- **결정:** Phase 3에서는 이 필드들을 자유서술 문자열로 받되, 사용자가 실사용하며 카테고리 목록을 수집한다. 목록이 굳으면 `promptVersion`을 올리면서 enum으로 승격.
- **대안:**
  - 지금 enum 확정 → 탈락. 잘못된 라벨링이 초기부터 축적됨.
- **비고:** Hook Code A–M의 정의는 사용자가 별도 파일(`docs/HOOK_CODES.md`)로 정리해서 넘겨주면, Phase 3 프롬프트에 삽입한다.

## D-005 · 초기 인증은 없음(URL 비공개)

- **상태:** proposed
- **날짜:** 2026-08-21
- **맥락:** 팀 내부 도구이고, 초기 사용자는 소수. 로그인 시스템은 만들 시간·유지비용 대비 가치가 낮다.
- **결정:** 배포 URL을 아는 사람만 접근한다는 전제로 인증 없이 출시. 실제 유출 위험이 감지되면 Vercel Password Protection 또는 얇은 자체 세션 추가.
- **대안:**
  - 처음부터 Google OAuth → 탈락. 지금 없어도 되는 인프라.
- **비고:** 그래도 API Route는 서버 전용이며 키가 응답에 실리지 않는다는 원칙은 인증 유무와 무관하게 유지.

## D-006 · 배치 중간 상태는 초기에 저장하지 않음(옵션)

- **상태:** proposed
- **날짜:** 2026-08-21
- **맥락:** Phase 4에서 "중간에 새로고침해도 결과 유지"를 넣으면 localStorage 관리 코드가 늘어난다.
- **결정:** 첫 배포에서는 새로고침 시 결과 사라짐을 허용. 사용자가 실제로 문제를 겪을 때 localStorage 저장 추가.
- **대안:**
  - 처음부터 IndexedDB → 탈락. 지금은 오버스펙.
- **비고:** 배치 실행 중 브라우저 닫지 말라는 안내문을 표시.

## D-007 · Claude 응답은 항상 서버가 스키마 재검증·등급 재계산

- **상태:** accepted
- **날짜:** 2026-08-21
- **맥락:** AI가 등급 계산을 틀리게 하는 경우가 존재. 클라이언트가 그대로 믿으면 데이터 신뢰가 무너진다.
- **결정:** 서버 API가 응답을 Zod로 검증하고, `core.grade`와 `passedCount`는 서버에서 gates 결과를 근거로 재계산해 덮어쓴다.
- **대안:**
  - AI 값을 그대로 사용 → 탈락. 재현성·신뢰성 부족.
- **비고:** "AI는 관찰자, 규칙은 코드가 판정한다"는 원칙을 프로젝트 전반에 적용.

## D-008 · 파일 파싱은 브라우저에서, 서버에는 텍스트만

- **상태:** accepted
- **날짜:** 2026-08-21
- **맥락:** Excel 파일을 서버에 업로드하면 저장 경로·삭제 정책·개인정보 흐름 등 부가 문제가 늘어난다.
- **결정:** SheetJS로 브라우저에서 파싱. API에 보내는 건 분석 대상 텍스트 최소 필드만.
- **대안:**
  - 서버에서 파싱 → 탈락. 파일 수명 관리 문제.
- **비고:** 사용자 컴퓨터 밖으로 파일이 나가지 않는다는 프라이버시 이점도 있음.

## D-009 · Claude 모델은 `claude-sonnet-4-5`로 고정 시작

- **상태:** accepted
- **날짜:** 2026-08-21
- **맥락:** Sonnet은 품질·비용 균형이 좋다. Opus는 이 판정 작업에 과잉일 수 있다.
- **결정:** 초기 모델 `claude-sonnet-4-5`. 실제 품질이 부족하면 특정 필드만 Opus 4.7로 실험.
- **대안:**
  - Opus 처음부터 → 탈락. 비용이 배치 단위에서 급증.
- **비고:** 모델 변경은 항상 DECISIONS에 새 항목을 추가하며 이유를 남긴다.

## D-010 · Scout는 공식 Threads API만, URL 크롤링은 부차 기능

- **상태:** accepted
- **날짜:** 2026-08-21
- **맥락:** 임의 URL 스크래핑은 차단·법적 회색 지대·유지비용이 크다.
- **결정:** Threads 공식 keyword search API가 유일한 자동 수집 경로. 원문이 필요하면 사용자가 textarea에 붙여넣는다.
- **대안:**
  - Puppeteer/Playwright로 페이지 렌더링 → 탈락. 유지비 큼, 정책 위험.
- **비고:** 이 결정은 Scout 착수 시점에 재확인.
