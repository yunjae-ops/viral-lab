# SPEC.md — Viral Lab 기능 사양

## 0. 한 줄 요약

Threads 바이럴 콘텐츠 업무용 내부 웹도구. Next.js 한 프로젝트 안에 두 페이지.

- `/review` — 내가 쓴 Threads 초안을 내 원칙으로 평가
- `/scout` — Threads에서 새 레퍼런스를 수집 (Review 완성 후에만 개발)

---

## 1. `/review` 사양

### 1.1 사용자 시나리오

1. 사용자가 자신이 관리 중인 Excel 파일을 브라우저에서 업로드한다.
2. 도구가 Excel의 실제 Header 행을 자동으로 찾고, 몇 행이 감지됐는지 사용자에게 보여준다.
3. 사용자가 "분석 시작" 버튼을 누른다.
4. 도구가 각 행(콘텐츠 초안)에 대해 Claude로 Core Grade + Diagnostic을 계산한다.
   이미 로컬 캐시(§1.7)에 동일 입력의 결과가 있으면 Claude를 호출하지 않고 캐시를 사용한다.
5. 진행률이 실시간으로 보인다 (예: `47 / 120`, 그중 캐시 히트 12건 표시).
6. 모두 끝나면 표에 결과가 표시되고 Portfolio Analysis(전체 통계)가 상단 카드로 나타난다.
7. 사용자가 "결과 다운로드" 버튼을 누르면 원본을 건드리지 않고 `..._ANALYZED_YYYYMMDD_HHmm.xlsx` 파일이 만들어진다.

### 1.2 입력 Excel 형식

- 일반적인 "첫 행 = Header" 형식이 아니다. 앞쪽에 빈 행 또는 안내문이 있을 수 있다.

- **필수 Header (반드시 포함):**
  - `순서`
  - `/제목` — Threads 레퍼런스 URL
  - `리뷰내용` — 사용자가 작성한 콘텐츠 초안

- **선택 Header (있으면 사용, 없어도 분석 가능):**
  - `이미지 파일명` — 있으면 결과 표/ANALYZED 파일에 그대로 실려 나감
  - `레퍼런스 원문` — 있으면 레퍼런스 vs 초안 비교 활성화, 없으면 초안 단독 평가

- **Header 별칭 (동일 의미로 인정):**
  - `/제목` = `레퍼런스 링크`
  - `리뷰내용` = `작성안` = `작성한 글`

- **Header 자동 감지 규칙:**
  - 처음 20행을 훑는다.
  - 각 셀 문자열은 `trim`(앞뒤 공백 제거) 후 비교.
  - 필수 Header 3종(정확 일치 또는 위 별칭)이 **모두** 포함되는 첫 행을 Header 행으로 확정.
  - 못 찾으면 명확한 에러: "Header를 찾지 못했습니다. 필수 컬럼: 순서, /제목(=레퍼런스 링크), 리뷰내용(=작성안=작성한 글)".

### 1.3 Core Grade (핵심 판정)

각 콘텐츠 초안 1개에 대해 4개 Gate를 통과했는지 판정.

| # | Gate 이름 | 통과 기준 |
|---|-----------|-----------|
| G1 | 본문 완결성 | 질문/댓글에 의존하지 않고 본문에서 내용이 완결되는가 |
| G2 | 발견/전환 | 발견 또는 전환의 순간이 존재하는가 |
| G3 | 서사 완결 | 서사가 본문 안에서 완결되는가 |
| G4 | 결과·원인 구조성 | 결과의 원인이 구체적이고 구조적으로 활용 가능한가 |

**등급 계산 (확정):**
- 4개 통과 → **A**
- 3개 통과 → **B**
- 0–2개 통과 → **FAIL**

**C·D 등급은 존재하지 않는다.** 등급 enum은 `"A" | "B" | "FAIL"` 3종.

각 Gate는 `pass | fail`과 짧은 근거 문장(evidence) 1개를 함께 반환.
등급은 서버가 gates 결과를 근거로 항상 재계산해 덮어쓴다 (D-007).

### 1.4 Diagnostic (참고 지표, Core Grade와 분리)

Core Grade와 절대 섞지 않는다. UI에서도 별도 섹션.

**enum으로 고정된 3축:**

- **Hook Code:** `A|B|C|D|E|F|G|H|I|J|K|L|M` — 정의는 `docs/HOOK_CODES.md` (OTHER 없음)
- **감정태도:** `절박함 | 시크함 | 순수감탄 | 놀람 | OTHER`
- **화자:** `본인 1인칭 | 딸-엄마 관찰 | 친구-친구 관찰 | 순수 목격자 | OTHER`
- **정보공개방식:** `직접서술 | 리스트 | 대화체 | 선언문 | OTHER`

OTHER를 반환할 때는 `otherLabel`(짧은 자유서술 라벨)을 함께 반환해야 한다. Zod가 이 조건을 강제한다.

**그 외 diagnostic 필드:**

- Hook Code 근거 한 줄 (`hookCodeReason`)
- 리스트형 항목의 문법적 균질성 (해당 시 pass/fail + 근거)
- 제품·판매 메시지 비중 (0–100% 정수)
- 레퍼런스와의 과도한 문장/디테일 유사성 (레퍼런스 원문이 있을 때만; 유사 문장 인용)
- 사실 검증이 필요한 건강/효능 주장 목록 (문자열 배열)
- 수정이 필요한 핵심 포인트 (문자열 배열, 최대 3개)

### 1.5 Portfolio Analysis (Excel 전체)

전체 행이 분석된 뒤 1회 계산.

- Hook Code A~M 별 사용 개수(막대)
- 감정태도 분포(막대, `OTHER`는 별도 표시)
- 화자 분포(막대, `OTHER` 별도)
- 정보공개방식 분포(막대, `OTHER` 별도)
- 등급 분포 (`A`, `B`, `FAIL`)
- 과사용 경고: 어떤 카테고리가 상위 임계치(예: 40% 초과)이면 자동 경고
- 다음 소재에서 비어 있는 방향 추천 (자유서술 텍스트, Claude가 생성)

집계·경고는 서버 코드가 결정적으로 계산. Claude 호출은 "다음 소재 추천" 자유서술에만 사용 (D-002).

### 1.6 결과 저장 방식 (파일)

- **화면:** 표 + 상단 Portfolio 카드.
- **다운로드:** 브라우저 다운로드로 새 xlsx 파일 제공.
  - 파일명: `{원본이름}_ANALYZED_{YYYYMMDD_HHmm}.xlsx`
  - 원본 시트 유지 + 다음 시트 추가:
    - `Analysis` — 원본 행 + 등급 + 각 Gate 결과 + Diagnostic 요약 컬럼들
    - `Portfolio` — 집계표 + 경고 + AI 자유서술

### 1.7 로컬 캐시 (row-level, localStorage)

- Supabase·IndexedDB는 사용하지 않는다.
- localStorage에 각 행 분석 결과를 캐시한다.
- **캐시 키:** SHA-256 해시(`draft` + `` + `refOriginal ?? ""` + `` + `promptVersion`).
  > 용어: SHA-256 = 같은 입력엔 항상 같은 짧은 문자열이 나오는 해시 함수. 입력이 달라지면 값도 달라진다.
- **동작:**
  - 분석 시작 시, 각 행에 대해 캐시 조회. 히트하면 Claude를 호출하지 않고 그 결과를 사용.
  - 사용자가 "이 행 강제 재분석" 또는 "전체 강제 재분석" 버튼을 누르면 캐시를 무시하고 새로 호출한 뒤 캐시를 갱신.
  - 새로고침 후 다시 파일을 업로드해도 같은 초안·원문·promptVersion이면 결과가 즉시 복구된다.
- **엔트리 스키마:** `{ key, promptVersion, analyzedAt, result: RowAnalysis }`
- **크기 관리:** localStorage 총량 4MB에 근접하면 오래된 것부터 축출(LRU) — 초기 구현에서는 단순 timestamp 기준.
- **초기화:** 헤더 우측 "캐시 비우기" 버튼 하나로 전체 삭제.

### 1.8 성능·비용

- 초기 동시성 = 3 (Claude 호출 병렬 3개까지).
- 분석 시작 전 다이얼로그: "총 N건, 그중 캐시 히트 K건. 실제 Claude 호출 건수 (N-K)+1(포트폴리오 1회). 계속?"
- 실패한 행은 표시만 하고 나머지는 계속 진행. 실패한 행만 재시도 버튼 제공.

### 1.9 인증

- **개발/빈 UI 단계 (Phase 1~2):** 인증 없음. Claude API endpoint가 아직 존재하지 않으므로 유출 위험이 없다.
- **Claude API endpoint가 Vercel에 공개되는 시점부터 (Phase 3 이후):** 최소한의 shared-password 인증을 적용.
  - 방식: 브라우저에서 비밀번호 입력 → 서버가 `REVIEW_SHARED_PASSWORD` 환경변수와 비교 → 성공 시 HttpOnly 세션 쿠키 발급 (예: 30일).
  - Google OAuth 등 복잡한 인증은 도입하지 않는다.
  - 세부는 D-005 참조.

## 2. `/scout` 사양 (Review 완성 후에만 개발)

### 2.1 사용자 시나리오

1. 사용자가 검색 키워드와 옵션(TOP/RECENT, 기간, 최대 개수)을 입력한다.
2. "수집 실행" 버튼을 누른다 — **자동 스케줄 없음, 수동 트리거만.**
3. 도구가 Threads 공식 keyword search API를 호출해 결과를 받아온다.
4. 기존에 저장된 것과 중복 제거 후 Supabase에 upsert.
5. 결과 테이블: `text`, `permalink`, `username`, `timestamp`, 수집 태그.
6. 각 행 옆에 "원문 보기"(permalink 새 창) + "원문 붙여넣기"(textarea, 자동 스크래핑 실패 대비 수동 fallback).
7. 사용자가 원하면 특정 행을 Review 형식으로 밀어넣을 수 있다(선택 기능, Phase 후반).

### 2.2 데이터 저장

- Supabase 테이블 `scout_items` (스키마는 `docs/DATA_CONTRACT.md` §5).
- 중복 판정 키: `permalink` (unique).

### 2.3 자동화

- 자동 수집은 마지막 Phase에서만.
- 방식: Vercel Cron Jobs 1개.
- 자동 수집 실패 시 관리자용 로그 페이지에 남긴다.

### 2.4 스크래핑 정책

- 공식 API 결과 필드만으로 처리한다.
- 임의 URL의 본문 크롤링을 만들지 않는다. 필요하면 사용자가 원문을 붙여넣는다.

## 3. Non-Goals (지금은 안 만드는 것)

- 다중 사용자 계정·권한 시스템
- 팀 협업(코멘트, 승인 흐름)
- 모바일 전용 UI (반응형만 최소 지원)
- Threads 외 플랫폼 지원
- AI 파인튜닝
- 실시간 알림
- 자체 이미지 저장/CDN

## 4. 열려 있는 결정 (사용자 확정 필요)

- 없음(현 시점). 이전 열린 항목은 모두 확정됨:
  - Core Grade C/D → 폐지, `A|B|FAIL`만 존재
  - Hook Code A~M → `docs/HOOK_CODES.md`로 확정
  - Diagnostic 카테고리 → enum + OTHER + otherLabel로 확정
  - 인증 정책 → shared-password (D-005)
  - 캐시 정책 → localStorage row-level cache (D-006)
